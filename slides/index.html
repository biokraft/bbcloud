director it · cto

Throughput, without a new platform

  • No licence, no server, no procurement. MIT, one binary, the token in the OS keychain.
  • Works with the agents already in use — Cursor, Claude Code, Codex, OpenCode — and the Atlassian MCP.

technical team lead

Review load worth steering

  • Reviewers from file history, instead of eleven by default.
  • "Ready to merge?" in one call: build, conflicts, open threads.
  • A 57-thread round becomes a checklist, answered in-thread with commit hashes.
product manager

Answers without chasing a developer

  • Ticket replies written for the PM first: what users get, how to test — then the tech tail.
  • "Is WEB-3497 in review, and is it green?" — answered from Jira and Bitbucket at once.
  • Updates edit the same comment instead of stacking new ones.
developer

Stay in the editor

  • No tab for reading, answering, describing or retargeting a PR.
  • "Resolve the merge conflicts on <link>" — fetched, merged, tested, explained.
  • Description and ticket reply are drafts for approval, not chores.

where it comes from

Seán Baufeld wrote bb and published it under MIT — an independent Rust rewrite of the PHP bb-cli. It has grown since: reviewer suggestions from file history, selective review context for agents, the agent skills, and the macOS keychain fix.

what it is

One Rust binary. bb <noun> <verb>, like gh. --json on every command, and it ships the skills that teach an agent to use it.

alive

Six releases since early September, v0.21 to v0.25.0. Issues and pull requests welcome.

act iiicrossing the threshold

Three commands. Then it knows the repository.

1 · install

Homebrew, one static binary, no runtime. Also install.sh, nix, cargo.

2 · log in

An Atlassian API token, checked before it is stored in the keychain. A wrong scope fails here, not three commands later.

3 · teach the agent

Writes the bundled skills for Cursor, Claude Code, Codex and OpenCode. No network needed — they ship inside the binary.

no config

The repository comes from the git remote. In any Bitbucket checkout, bb pr list just works.

act ivtrial 2 · for reviewers

A description the reviewer actually finishes.

TL;DR · PR #3396

  • Android installs the app bridge twice: a bare object exposing only postMessage, then bridge.js replaces it. Two bugs came out of that.
  • A wrapper built in that window stayed bound to the bare object — every native call silently did nothing. Calls before the swap threw a TypeError.
  • The bridge is now resolved per call, which settles both.

What to look at

  • AppBridge.ts — the fix. getBridge() per call; ready() idempotent, which removed an if (!isReady) from 15 methods.
  • AppBridge.types.ts — call is optional, so the 16 ?. guards are compiler-enforced.
  • Read the native object install specs, not the "does not throw" case — that one passes even with the fix reverted.
optional skill · pr-description

The reviewer already has the diff. The description supplies what a diff cannot: intent, priority, and what is not in the diff. 3 TL;DR bullets, 4 review-focus bullets, one screen.

Say it twice. Nothing doubles.

act vunder the hood · for the cto and security

Boring, on purpose.

a contract for machines

--json on every command; stdout is one JSON value and nothing else. Exit codes are the API: 0 ok, 1 error, 2 not logged in, 3 not found.

the token

An Atlassian API token in the OS keychain, and nowhere else. Never printed; there is no auth show. App passwords were removed on 2026-07-28.

least privilege

Four scopes cover the PR workflow: read:user, read:pullrequest, write:pullrequest, read:repository.

no shell, no openssl, no unsafe

Git calls are argument vectors, never sh -c. rustls only. #![forbid(unsafe_code)]. Redirects stay on the same origin.

one host

Talks to api.bitbucket.org only. bb update checks GitHub releases without credentials.

cost

MIT. No server, no seats, no vendor. Homebrew for macOS, binaries for Linux. The tokens it uses are the ones a browser session already uses.

No new service to review. A CLI, a token that already exists, and one host it talks to.

backup · the questions this deck skips

Does this replace the Atlassian MCP?

No. The MCP owns Jira — the ticket, its comments, the reply. bb owns Bitbucket — pull requests, threads, builds, conflicts, file history. They don't overlap, which is why the combination works.

Can an agent merge or approve?

Not through bb: there is no approve, merge or decline command. Everything else acts with the account's token, so an agent inherits the same permissions. Confirmation prompts on resolve and request-changes help people; an agent can pass --yes, so they are not a boundary. Review culture and Bitbucket's merge checks are.

Where do the numbers come from?

Read-only git log, git shortlog, bb pr list --json, bb pr view --json and bb pr reviewers suggest on one real product team's repository in September 2026. Names, ticket keys, pull request numbers and file paths are changed; the counts are not. The theme clustering of the 57 threads is by keyword, so treat the per-theme counts as approximate.

Is it safe to hand a token to a tool like this?

The token goes to the OS keychain and nowhere else — no file, no config directory, no child-process environment. auth status can only print the last four characters, and a test fails the build if anyone adds an auth show. On macOS the secret is passed on stdin, never in argv.

Why does reviewer suggestion need --acknowledge-private-data?

It reads file paths, colleague names, dates and account ids from commit history and hands them to whatever is on the other end — possibly a model. The flag makes a person say yes to that first.

What about CI?

Anything that posts a build status to Bitbucket — Jenkins, Bitbucket Pipelines, others. bb reads that status and the run URL. It does not fetch CI logs; open the URL for those.

Isn't bulk-answering review comments disrespectful to reviewers?

The opposite is the goal: the agent replies on every thread with the commit that addressed it, so a reviewer sees exactly what changed for their point. Design questions get a reasoned answer for you to check, not a "done". And you decide what gets resolved.

What does it cost?

Nothing to buy or host: MIT licence, one binary, Homebrew, an install script, nix, cargo or a release download. It uses an existing Atlassian API token and the coding agent already in use.

What if a skill disagrees with the project?

Edit it. Skills are plain Markdown. bb skill install never overwrites a skill that was edited; it reports it and leaves it alone. The optional skills can be pasted into AGENTS.md.

Who maintains it, and how are releases made?

github.com/biokraft/bbcloud is maintained in the open and contributions are welcome. Seán Baufeld started it; releases are automated: the version comes from cargo-semver-checks, and merging the release PR publishes to crates.io, builds four binaries with checksums and updates the Homebrew formula.

What would a pilot actually measure?

Two things countable without new tooling: review round-trips per PR (from bb pr view --json) and time from a "please resolve merge conflicts" comment to a green build. Four volunteers, four weeks, compared with their previous four weeks.

Is Windows on the roadmap?

Not stated. macOS arm64 and x86_64, Linux x86_64 and arm64. If you need Windows, open an issue — that's a conversation, not a promise.
